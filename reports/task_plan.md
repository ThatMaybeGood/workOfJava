# 任务计划：reports 项目新增 ETL 定时抽取功能

## 目标
在现有报表展示项目（reports）内新增一套独立、可配置的 ETL 抽取功能：前端建立抽取任务，后端定时执行，实现「抽取 → 转换映射 → 写入/更新」完整流程，且不触碰现有报表展示的数据源配置与代码。

## 用户原始需求（转述梳理）
> 当前目录是展示报表的。需要在此项目下新增功能：能定时执行 ETL 抽取数据，前端能建立抽取任务。
> 抽取有两种数据来源方式：
> 1. 调用 WebService 接口出参 → 转换映射 → 写入/更新对应表
> 2. 调用存储过程出参（游标）→ 转换映射 → 写入/更新对应表
> 界面要能：对数据来源调试出参 → 根据出参可视化映射到目标数据库的表。
> 整个过程：抽取 → 转换映射 → 写入/更新。
> 设计上可能连接多个数据库，可能是数据来源库，也可能是目标数据源库，界面可配置。
> **关键约束**：现在项目已配置一个数据库（用于报表展示），不要改动它；目前「目标数据源库」和「报表展示库」是同一个。

## 用户对关键问题的确认（2026-08-17）
1. **ETL 元数据** → 按推荐：独立 H2 库（不影响现有 Oracle 报表库）。
2. **WebService** → SOAP(XML) 和 REST(JSON) **两种都要支持**；前端能解析层级出参（嵌套对象/数组），直接在界面做字段映射。
3. **存储过程** → Oracle 的 `SYS_REFCURSOR` 游标出参。
4. **写入模式** → 类似 Kettle 表输出：界面选择目标表 + 写入模式（插入/更新/存在则更新否则插入）；配置「查询索引」（唯一条件）→ 命中则更新指定字段，未命中则插入。
5. **调度** → cron 定时即可，**必须支持手动触发**（调试各环节跑通后再改定时跑）。
6. **日志** → 需要：界面维护日志保存时间（保留策略）；界面能看清每个调度任务的运行情况（执行历史/各环节状态），出问题可追溯查询。
7. **（补充）逐环节调试** → 前端也需具备**每个节点的调试功能**：抽取任务任一环节出问题时，直接在界面逐个环节调试，排查问题出在 抽取 / 转换映射 / 写入 哪一环。
8. **（补充）内存分批流式** → 出参可能过大，避免整批载入内存撑爆：抽取→转换→写入按**批**流水线推进，内存峰值恒定。
9. **（补充）并发互斥 + 重试** → 同一任务手动/定时不允许并发跑（任务级互斥锁）；失败可配自动重试。
10. **（补充）增量抽取** → 支持按增量字段/时间占位符只抽上次同步后的新数据，避免重复全量。
11. **（补充）非 Oracle 目标库** → 数据源类型可配（Oracle/MySQL/达梦/SQLServer/PG/H2），写入 SQL 按方言生成。
12. **（补充）失败告警通知** → 任务失败/连续失败时通知（邮件/钉钉/Webhook 可配）。
13. **（最后确认）核心定位** → 用户明确：主要就是「对不同来源的数据抽取转换后写入到库」。**报表库与写入库当前是同一个，但将来可能不同** → 目标库必须始终是「界面配置的数据源」，不得把「报表库=master」写死为唯一目标库；目前场景下用户把同一个 Oracle 库既作报表库又作为目标数据源配置即可（提供「复用现有 master 连接池」便捷项，但仍是可选而非唯一）。

## 方案设计（阶段 2 产出）

### 0. 总体架构
```
[前端 reports-web/etl/ 页面组（原生 JS）]
  数据源管理 | 任务配置(含调试出参) | 字段映射 | 调度与历史 | 日志管理
        │ REST API
[后端 com.reports.etl.* 模块]
  ① 元数据访问（H2 独立库 etl_meta）
  ② 数据源注册中心（运行时动态创建 Druid 连接池）
  ③ 抽取器 Extractor：WebServiceExtractor / ProcedureExtractor
  ④ 转换器 Transformer：字段映射引擎（支持层级展开 / dot-path）
  ⑤ 写入器 Writer：InsertWriter / UpdateWriter / UpsertWriter
  ⑥ 调度器 EtlScheduler（@Scheduled + cron + 手动触发）
  ⑦ 日志与执行历史（task_log / step_log + 保留策略清理）
```

### 1. ETL 元数据存储（独立 H2）
- 新建 H2 文件库：`./data/etl_meta`（`jdbc:h2:file:./data/etl_meta`，由 reports 应用内嵌，**与 Oracle 报表库完全隔离**）。
- 独立数据源 Bean（`etlMetaDataSource`），MyBatis-Plus 用 `@DS`/独立 SqlSessionFactory 绑定元数据表。
- 建表（初始化脚本 `src/main/resources/db/etl-h2.sql`，启动时执行）：
  - `etl_datasource`：数据源配置（名称/驱动/URL/账号/加密密码/用途 SOURCE|TARGET/连接池参数）
  - `etl_task`：任务主表（名称/抽取类型 WEBSERVICE|PROCEDURE/源数据源ID/目标数据源ID/目标表/写入模式/cron/启用状态/备注）
  - `etl_task_ws_config`：WebService 配置（URL/方法/请求头/SOAPAction/请求体模板/出参定位路径）
  - `etl_task_proc_config`：存储过程配置（过程名/参数列表 JSON/游标参数名）
  - `etl_mapping`：字段映射（任务ID/源字段 dot-path/目标字段/目标列类型/默认值/是否更新字段/排序）
  - `etl_task_log`：任务执行历史（任务ID/开始/结束/状态/读取行数/写入行数/错误信息）
  - `etl_step_log`：步骤日志（执行ID/步骤 EXTRACT|TRANSFORM|LOAD/状态/耗时/详情）
  - `etl_log_config`：日志保留策略（保存天数/是否自动清理）
  - （任务表补充字段）`max_rows`、`batch_size`、`max_pages`、retry 配置、增量配置（增量字段/初始值）、告警配置（渠道/地址/连续失败阈值）

### 2. 数据源管理（运行时多数据源）
- `EtlDataSourceRegistry`：根据 `etl_datasource` 记录动态创建 DruidDataSource，缓存连接池；界面增删改后刷新注册中心。
- 每次执行任务时按「源/目标」从注册中心取连接，**不复用、不修改现有 `DynamicDataSource`**。
- 目标库 = 现有 Oracle 报表库（`168.168.235.105:1521/yuanqi`）时，可把它作为一条「目标数据源」配置，或直接提供「使用现有 master 数据源」快捷选项（不重复建池）——但**这一点仅是便捷项而非唯一目标**，因为将来报表库可能与写入库分离，目标库始终以界面配置的数据源为准。
- 密码加密存储（可复用项目现有加解密工具或自建对称加密）。
- 接口：
  - 数据源 CRUD、连接测试（`SELECT 1`）
  - 取表/视图列表、取表字段（JDBC DatabaseMetaData）

### 3. WebService 抽取（SOAP + REST）
- **SOAP**：OkHttp POST + 请求体模板（可配置命名空间/参数占位）+ SOAPAction Header → 响应 XML → `jackson-dataformat-xml` 解析 → 层级展开。
- **REST**：OkHttp GET/POST，JSON 请求体模板 → 响应 JSON → `jackson` 解析 → 层级展开。
- **层级展开**：嵌套对象/数组递归展开为「平铺字段路径列表」+「路径 → 值」映射，供前端树形展示与映射（如 `data.items[*].patientName`）。
- **调试出参**：`POST /api/etl/ws/debug` 保存配置→实际调用→返回（a）层级字段树（含样例值）（b）首行样例数据；前端据此做映射。
- 支持从出参中定位数组主体（如 `response.list` / `data.records`）作为「行集合」，行内字段作为映射源。

### 4. 存储过程抽取（Oracle SYS_REFCURSOR）
- JDBC `CallableStatement.registerOutParameter(idx, OracleTypes.CURSOR)` → 读取 `ResultSet` → 按列名转 List<Map>。
- 参数支持 IN 参数（绑定值来自任务配置/常量）；可配出参游标参数序号。
- **调试**：`POST /api/etl/proc/debug` → 实际调用 → 返回游标结果集的列结构 + 样例数据，前端据此映射。

### 5. 字段映射与转换（可视化，类似 Kettle 的「字段选择/值映射」）
- 前端映射页：左侧**出参字段树**（层级展开，勾选/拖拽）→ 右侧**目标表字段列表**（下拉选中目标列）→ 生成 `etl_mapping`。
- 每条映射：`源字段(dot-path)` → `目标列` + `默认值` + 是否参与「更新字段」。
- Transformer 按 dot-path 从行数据取值，做基础类型转换（字符串/数字/日期/空值处理）。

### 6. 写入模式（类似 Kettle 表输出 + Merge）
- 任务级配置 `写入模式`：
  - **INSERT**：批量插入（`insert into tgt(...) values(...)`）。
  - **UPDATE**：按「查询索引」字段定位，更新指定的「更新字段」。
  - **UPSERT**（存在则更新否则插入，Kettle Merge 语义）：任务配置「查询索引」= 唯一条件字段列表（如主键/业务唯一键）；对每行：`MERGE INTO tgt USING ... WHEN MATCHED THEN UPDATE SET <更新字段> WHEN NOT MATCHED THEN INSERT(...)`（Oracle 原生 MERGE）或先查后插的 UPDATE-else-INSERT。
- 「更新字段」= 映射中勾选了「作为更新字段」的目标列；「查询索引」= 任务级配置的唯一键。

### 7. 调度与手动触发
- `EtlScheduler`：应用启动后从 `etl_task` 加载启用任务，`@Scheduled(cron=...)` 动态注册（用 `TaskScheduler` 按 cron 调度，支持热更新）。
- **手动触发**：`POST /api/etl/task/{id}/run` 单次同步或异步执行（调试用）；调试跑通后只需勾选启用 + 配 cron 即转定时。
- 暂停/恢复：改任务启用状态即可（调度器热加载）。

### 8. 日志与保留策略
- 每次执行写 `etl_task_log`（总览）+ `etl_step_log`（EXTRACT/TRANSFORM/LOAD 各环节：状态/耗时/行数/错误详情），前端可按任务/时间查询执行历史，点开看各环节时间线。
- 日志文件：项目内独立目录 `./logs/etl/`（每任务按天文件），与 reports 现有日志分开，便于排查。
- 保留策略：`etl_log_config` 配「日志保存天数」，后台定时清理超过天数的 `etl_task_log/etl_step_log` 与日志文件；界面可维护。
- 前端「日志管理页」：设保存天数 + 查看保留策略。

### 9. 后端接口清单（`/api/etl/*`）
- 数据源：CRUD、连接测试、表/视图列表、表字段
- WebService：配置保存、`debug`（出参调试 → 字段树+样例）
- 存储过程：配置保存、`debug`（游标结果 → 列结构+样例）
- 映射：按任务 CRUD（增删改映射行）
- 任务：CRUD、`run`（手动执行）、暂停/恢复、执行历史查询、执行详情
- **调试（逐环节）**：`debug/extract`、`debug/transform`、`debug/load`（默认 dry-run，force 才真实写）、`debug/run-all`
- 日志：保留策略读写、任务执行历史/步骤日志查询
- 告警：通知配置读写、测试发送

### 11. 内存分批流式（内存保护，核心设计）
> 问题：出参可能过多，整批载入内存会 OOM，导致程序无法正常抽取。
> 原则：**不以总量为内存复杂度，而以批次为单元**，抽取→转换→写入流水线式推进。

- **抽取分批**：
  - WebService：支持**分页拉取**（pageNo/pageSize 参数占位），配 `max_pages`/`max_page_size` 循环上限，逐页拉取；响应体若本身含数组可整页取。
  - 存储过程游标：JDBC 流式批读，`Statement.setFetchSize(batchSize)`，每次只读一批，读完即写。
- **转换/写入按批消费**：抽取器输出 **BatchIterator**（按批吐行，每批 `batch_size` 可配，默认 500），转换对当前批做映射，写入器对当前批提交一个事务（批末 commit）；批内失败仅回滚该批（是否继续由任务配置决定）。
- **内存峰值 = 单批行数 + 元数据**，不随数据总量增长。
- **保护上限**：任务级 `max_rows` 硬上限，超限即中止 + 记录告警（防死循环/配置错误拉爆）。
- 调试 dry-run 时可限制只处理前 N 行（如 `debug_rows`），不整批处理。

### 12. 并发互斥 + 重试
- **任务级互斥锁**：同一任务同一时刻只允许一个执行实例（`ConcurrentHashMap<任务ID, 运行标记>` / DB 锁）；手动触发时若已有调度在跑，返回提示而非并发执行。
- **失败重试**：任务配 `retry_count`（默认 0）；某次整体失败且未超上限时，调度器按指数退避自动重跑。

### 13. 增量抽取
- 任务配 **增量模式**：`全量 / 增量`。
- 增量下配置 `增量字段`（如 UPDATE_TIME/业务日期）与**时间占位符**：`#today#`（当天）、`#lastTime#`（上次成功运行时间，存执行历史）、`#lastRunTime#` 等，抽取时替换进请求体/过程参数/SQL。
- 首次运行按给定初始值（或全量）拉取，之后只抽增量；任务执行成功即更新 `last_time` 游标。

### 14. 多数据库方言（非 Oracle 目标库）
- 数据源表加 `db_type`：ORACLE / MYSQL / SQLSERVER / POSTGRESQL / DM(达梦) / H2。
- 写入器按 `db_type` 生成方言 SQL：
  - INSERT/UPDATE 批量语句；
  - UPSERT：Oracle `MERGE INTO`、MySQL/PG `INSERT ... ON DUPLICATE KEY UPDATE` / `ON CONFLICT`、SQLServer `MERGE`、达梦同 Oracle、H2 `MERGE INTO`。
- 元数据管理始终用独立 H2，与目标库方言无关。

### 15. 失败告警通知
- 任务配 `告警配置`：`通知渠道（mail/dingtalk/webhook）` + `接收地址` + 可选 `连续失败 N 次才通知`。
- 调度器在任务失败态自动调用通知（Spring Mail / OkHttp 发 webhook/钉钉）。
- 通知内容：任务名、执行ID、失败环节、错误摘要。

### 16. 逐环节调试（用户补充需求，核心设计）
> 目标：任一环节出问题时，界面可逐步调试定位「卡在抽取 / 转换映射 / 写入哪一环」。

- **调试粒度＝三个环节，每环节可独立跑**：
  1. **① 抽取调试** `POST /api/etl/debug/extract`
     - 输入：任务ID
     - 执行：仅调用 WebService / 存储过程 → 拿原始出参（XML/JSON/游标结果集）
     - 返回：原始出参预览 + 解析后的字段树 + 行集合 N 行样例 + 该环节耗时/错误
     - 用途：验证「能不能抽到、出参解析对不对」
  2. **② 转换映射调试** `POST /api/etl/debug/transform`
     - 输入：任务ID + 可选行号
     - 执行：对已抽取的行集合跑字段映射引擎（按 etl_mapping 取值/转换）
     - 返回：每个源字段→目标列的取值结果 + 转换后的目标行样例 + 落库 SQL 预览
     - 用途：验证「映射配置对不对、字段名/类型转换对不对」
  3. **③ 写入调试** `POST /api/etl/debug/load`
     - 输入：任务ID + 模式（**尽力而试**=真实写入目标表 / **dry-run**=不真实写入只校验SQL）
     - 执行：按写入模式(INSERT/UPDATE/UPSERT)生成并执行 SQL
     - 返回：写入行数 / 受影响行 / 错误信息（含 SQL 与绑定参数）
     - 用途：验证「写入模式、查询索引、MERGE 逻辑对不对」
- **全链路一键调试** `POST /api/etl/debug/run-all`：依次跑①→②→③，各环节结果/耗时/错误汇总返回，前端分段展示（类似流水线视图）。
- **安全**：写入调试默认 **dry-run**（不真实改动目标表），界面显式勾选「真实写入提交」才执行真实写入；大表/线上库需二次确认。
- 前端「任务配置」页提供 **调试标签页**：步骤条（抽取→转换→写入）+ 每环节结果面板 + 错误高亮 + 可展开原始出参/SQL。

## 已做决策
| 决策 | 理由 |
|------|------|
| ETL 独立成新模块（后端 com.reports.etl.*，前端 reports-web/etl/） | 不侵入现有报表代码 |
| ETL 元数据存独立 H2 文件库 | 用户确认；彻底隔离 Oracle 报表库 |
| WebService 同时支持 SOAP+XML 与 REST+JSON，出参层级展开 | 用户确认 |
| 存储过程用 Oracle SYS_REFCURSOR 出参 | 用户确认 |
| 写入模式：INSERT/UPDATE/UPSERT(存在更新否则插入) + 查询索引 | 用户确认，Kettle 表输出语义 |
| 调度：@Scheduled cron + 手动触发 | 用户确认（先调试后定时） |
| 日志：独立目录 + 元数据表保留策略 + 界面维护与查询 | 用户确认 |
| **逐环节调试**：抽取/转换/写入三环节可独立调试 + 全链路一键调试；写入默认 dry-run | 用户补充确认（界面排查哪一环出问题） |
| **内存分批流式**：BatchIterator 按批抽→转→写，单批提交事务；max_rows 硬上限 | 用户提出出参过多撑爆内存风险，采取分批保护 |
| **并发互斥 + 重试**：任务级互斥锁防并发；失败配重试 | 用户采纳（手动/定时不打架，失败自动兜底） |
| **增量抽取**：增量字段 + 时间占位符（#lastTime# 等） | 用户采纳（避免重复全量） |
| **多数据库方言**：db_type 可配 Oracle/MySQL/SQLServer/PG/达梦/H2，写入按方言 | 用户采纳（异构目标库场景） |
| **失败告警通知**：mail/钉钉/webhook，可配连续失败阈值 | 用户采纳（第一时间发现） |
| 复用 okhttp / jackson-xml / jackson 做 WebService 与解析 | 依赖已具备 |
| 运行时数据源注册中心自建，不碰现有 DynamicDataSource | 界面动态配置多库所需 |
| 前端沿用原生 HTML/JS/CSS 风格 | 与 reports-web 现有页面一致 |
